OFFICIAL COURSE TITLE: CREATE AGENT

Module 1: Create an agent

By the end: you can build an assistant that follows instructions, uses tools and remembers the conversation.

0The skeleton

Every agent in the course starts from the same three moves: pick a model, wrap it with create_agent(), send it a message with invoke(). Everything else is an extra setting added to that call.

See the code 
from langchain.agents import create_agent
from langchain.messages import HumanMessage

agent = create_agent(model=model)

response = agent.invoke({"messages": [HumanMessage(content="Hello!")]})
print(response["messages"][-1].content)   # the last message is the answer
1Models

The model is the brain. Calling it directly (model.invoke) is a quick question with nothing attached. Calling it through an agent (agent.invoke) lets tools and memory join in. temperature sets the tone: low for steady answers, high for more variety.

See the code 
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="...", temperature=0.1)
print(model.invoke("A question").content)

for chunk in agent.stream(...):   # the answer arrives word by word
    ...
2Prompting

The system prompt is the job description: a role and rules that apply to every answer. Few-shot examples show the expected style. Structured output forces the answer into a fixed form, so your code can reuse it without parsing free text.

See the code 
from pydantic import BaseModel

class CapitalInfo(BaseModel):
    name: str
    location: str

agent = create_agent(
    model=model,
    system_prompt="You are a concise, clear assistant.",
    response_format=CapitalInfo,
)
data = response["structured_response"]
3Tools

A tool is a Python function the agent may decide to call. Its name, type hints and description are what the model reads to know when to use it. The agent decides; Python does the work.

User asks→Agent picks a tool→Python runs it→Agent answers
See the code 
@tool("square_root", description="Computes the square root of a number")
def square_root(x: float) -> float:
    return x ** 0.5

agent = create_agent(model=model, tools=[square_root])
4Memory

By default, an agent forgets everything between two calls. Give it a checkpointer (its notebook) and reuse the same thread_id (the page number): the conversation picks up where it left off.

See the code 
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(model=model, checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "1"}}

agent.invoke({"messages": [HumanMessage(content="My favourite colour is green")]}, config)
agent.invoke({"messages": [HumanMessage(content="What is my favourite colour?")]}, config)
5Multimodal messages

One message can mix text, image and audio, each as a small block with the same shape. Just check that the model you picked accepts what you send.

See the code 
message = HumanMessage(content=[
    {"type": "text", "text": "Describe this image"},
    {"type": "image", "base64": img_b64, "mime_type": "image/png"},
])

OFFICIAL COURSE TITLE: ADVANCED AGENT

Module 2: Connect and orchestrate

By the end: your agent plugs into ready-made tools, keeps track of information, and shares the work with other agents.

1MCP

MCP (Model Context Protocol) is a standard plug: a server offers ready-made tools, and the agent loads them in one call instead of you writing them. The server can run on your machine (stdio) or online (streamable_http).

Agent→MCP server: "your tools?"→Tools ready to use

Windows tip: in a notebook, add the WindowsProactorEventLoopPolicy fix before connecting, or the connection fails.

See the code 
from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient({
    "local_server": {"transport": "stdio", "command": "python", "args": ["server.py"]}
})
tools = await client.get_tools()
agent = create_agent(model="gpt-5-nano", tools=tools)
2Runtime context

Information fixed for the whole run, like a visitor badge: who the user is, their role, their preferences. Tools read it through runtime.context. It never changes by itself: to change it, call the agent again with a new one.

See the code 
@dataclass
class ColourContext:
    favourite_colour: str = "blue"

@tool
def get_favourite_colour(runtime: ToolRuntime) -> str:
    """Get the favourite colour of the user"""
    return runtime.context.favourite_colour
3State

Information that changes during the conversation, like a whiteboard the agent keeps updating. You describe its fields once (state_schema), and tools write to it with Command(update=...).

See the code 
class CustomState(AgentState):
    favourite_colour: str

@tool
def update_favourite_colour(favourite_colour: str, runtime: ToolRuntime) -> Command:
    """Update the favourite colour once revealed."""
    return Command(update={
        "favourite_colour": favourite_colour,
        "messages": [ToolMessage("Updated", tool_call_id=runtime.tool_call_id)],
    })
4Multi-agents

A main agent delegates to specialists. The trick: each specialist is wrapped inside a tool, so the main agent calls it exactly like any other tool. Several focused agents work better than one agent with too many tools.

Main agent→Specialist 1Specialist 2→Combined answer
See the code 
@tool
def call_subagent_1(x: float) -> float:
    """Call subagent 1 to calculate a square root"""
    response = subagent_1.invoke({"messages": [HumanMessage(content=f"sqrt of {x}")]})
    return response["messages"][-1].content

OFFICIAL COURSE TITLE: PRODUCTION-READY AGENT

Module 3: Flexibility and control

By the end: your agent stays affordable, asks before risky actions, and adapts to who is using it. Most of it relies on middleware: code that runs around every call to the model, like a checkpoint each request passes through.

1Long conversations

Every old message is re-sent and paid for on each call. Past a threshold, SummarizationMiddleware swaps the oldest messages for a short summary. RemoveMessage deletes specific ones, for example after a tool call.

See the code 
SummarizationMiddleware(
    model="gpt-4o-mini",
    trigger=("tokens", 100),   # when to summarise
    keep=("messages", 1),      # what to keep as is
)
2Human-in-the-loop

Before a sensitive action, such as sending an email, the agent pauses and waits for a person, who can approve, reject, or edit the action. Reading emails goes through freely; only the listed actions stop.

Agent wants to send→Pause→Approve · Reject · Edit→Resume
See the code 
HumanInTheLoopMiddleware(interrupt_on={"send_email": True})

# then the person decides:
Command(resume={"decisions": [{"type": "approve"}]})
# {"type": "reject", "message": "..."}
# {"type": "edit", "edited_action": {...}}
3Dynamic agent

The agent changes with the situation: a bigger model for long conversations, more tools for an admin, a different prompt once the user is logged in. @wrap_model_call swaps the model or tools; @dynamic_prompt swaps the prompt.

See the code 
@wrap_model_call
def dynamic_tools_by_role(request, handler):
    role = request.runtime.context.user_role
    tools = [read_email, send_email, delete_email] if role == "admin" else [authenticate]
    return handler(request.override(tools=tools))

@dynamic_prompt
def adapt_prompt(request):
    if request.state.get("authenticated"):
        return "You are an email assistant."
    return "You are an authentication assistant."

BEFORE YOU START

Four traps worth knowing

Context or state?

Context is the badge: fixed for the whole run. State is the whiteboard: it changes as the conversation goes. The most common mix-up of the course.

model.invoke or agent.invoke?

The first talks to the bare model. The second goes through the agent, with its tools, memory and rules.

Middleware order

Middleware runs in the order you list it. Put human approval last, so it checks the final action.

A paused agent stays paused

After a human-in-the-loop pause, nothing moves until you resume it with Command(resume=...).
